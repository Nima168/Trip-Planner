2. Implementation Summary

Extended .github/workflows/ci.yml and added .github/workflows/deploy.yml, per specs_new/backend-spec.md §9's CI/CD contract.

  • ci.yml — backend job now runs against a real Postgres 16 service container: the pytest suite itself still uses in-memory SQLite (unchanged, tests/conftest.py), but a new step runs alembic upgrade head then downgrade base against the Postgres container, proving the migration chain round-trips cleanly on the real engine. The frontend job gained npm run lint and npm run build alongside the existing npm test. Added a workflow_call trigger so deploy.yml can reuse this whole workflow as its test gate instead of duplicating steps.
  • deploy.yml — triggered on push to trip_planner.AI and via workflow_dispatch (needed for a no-code-change redeploy after infra/scripts/restore.sh). Pipeline: test (calls ci.yml) → build-and-push (OIDC into AWS, build the backend Docker image tagged with the commit SHA, push to ECR) → migrate (runs alembic upgrade head as a one-off Fargate task using that new image, waits for it to stop, fails the job if its exit code isn't 0) → deploy (registers a new ECS task definition revision pointing at the new image, updates the service, waits for services-stable, then curls the CloudFront health URL). No AWS access keys — auth is via the OIDC deploy role from Phase 6.
Two real bugs found and fixed while cross-checking the new CI/CD code against the actual app code (not just against the spec):
  1. infra/modules/ecs/main.tf was injecting a container env var named ALLOWED_ORIGINS (copying backend-spec.md's loose wording literally), but the backend's actual app/config.py/.env.example reads CORS_ORIGINS — pydantic-settings' default env-var mapping. Left as written, the deployed container would have silently fallen back to config.py's CORS default (http://localhost:5173) and rejected every request from the real Vercel frontend. Fixed.
  2. backend/entrypoint.sh ran alembic upgrade head inline on every container start — a leftover pattern that directly conflicts with the plan's explicit design (a one-off migration ECS task, precisely because in-entrypoint migrations race when several tasks start concurrently during a rolling deploy). Removed the inline migration; deploy.yml's migrate job now owns it exclusively.

Also added two Terraform root outputs (ecs_private_subnet_ids, ecs_security_group_id) so the deploy workflow's one-off migration task launches into the same private-subnet/security-group network as the running service, and documented the 9 required GitHub Actions repository Variables in infra/README.md (all sourced from terraform output after Phase 6's apply).

9. Known Issues and Limitations

  • Nothing here has executed end-to-end — it depends on Phase 6's AWS infra actually being live, which it isn't yet in this session.
  • The migrate job's container override assumes the ECS container is literally named backend (matches infra/modules/ecs's local.container_name) — if that name is ever changed on one side, the other must change too.
  • No automatic rollback on a failed deploy: aws ecs wait services-stable will time out and fail the job, but the previous task definition revision keeps serving traffic until someone manually points the service back at it — there's no automated revert.
  • OIDC auth will fail with a generic-looking AssumeRoleWithWebIdentity error if github_oidc_sub (Phase 6) isn't the exact debug-token-derived value — a stale or guessed value is a likely first failure mode.
  • Single environment only — every merge to trip_planner.AI deploys straight to the one prod stack, per the plan's explicit no-staging-tier decision.
