2. Implementation Summary

Created a new infra/ Terraform root at the repo root, matching the plan's Phase 6 layout exactly: a environments/prod root module wiring together seven reusable modules (network, database, ecr, ecs, alb, cdn, iam-oidc), plus three operational shell scripts and a README runbook.

  • network — VPC with public subnets (ALB + single NAT Gateway) and private subnets (ECS + RDS), one NAT Gateway shared across AZs to control cost.
  • database — RDS Postgres (db.t4g.micro, free-tier eligible), reads its master password from the persistent Secrets Manager secret (never random_password) so it survives destroy/restore cycles; accepts a restore_from_snapshot variable for the restore flow.
  • ecr — one image repository with a lifecycle policy capping retained images.
  • ecs — Fargate cluster/service/task definition, CloudWatch log group, execution role (ECR pull + Secrets Manager read) and a currently-empty task role. The service ignores task_definition/desired_count drift so the CI/CD deploy step (Phase 7, not yet built) can update it directly without fighting Terraform.
  • alb — HTTP:80 listener + target group health-checked against /health.
  • cdn — CloudFront in front of the ALB, terminating HTTPS on the default *.cloudfront.net certificate (caching disabled, all headers/cookies/query strings forwarded — this fronts an API, not static content).
  • iam-oidc — GitHub Actions OIDC provider + a narrowly-scoped deploy role (ECR push, ECS deploy, iam:PassRole to the two ECS roles, Secrets Manager read) — no static AWS keys in GitHub.

The root module also creates the Secrets Manager entries the ECS task consumes: DATABASE_URL (built from the database module's output + the persistent password), a fresh JWT_SECRET (regenerates on every apply — acceptable per spec, it only logs users out), and AI_API_KEY (passed in via a sensitive variable). A standalone aws_security_group_rule in the root module links ECS→RDS on port 5432, deliberately kept out of the database module to avoid a module dependency cycle (RDS's security group needs ECS's SG id; ECS's task definition needs RDS's connection string).

scripts/backup.sh / destroy.sh / restore.sh implement the manual-RDS-snapshot backup/restore contract from backend-spec.md §9: snapshot-before-destroy (refusing to destroy if the snapshot doesn't complete), and restore-from-latest-snapshot on the next apply, with the two post-restore manual follow-ups (redeploy for ECR, update Vercel's API base URL for the new CloudFront domain) printed at the end of restore.sh.

7. Step-by-Step Manual Verification

These steps touch a real AWS account and cost money while running (NAT Gateway + ALB bill hourly). They were intentionally not run by the assistant — AWS account access wasn't available in this session, and creating/destroying real cloud infrastructure is exactly the kind of hard-to-reverse, cost-incurring action that should be confirmed and run by you.

  1. Run aws sts get-caller-identity to confirm your AWS CLI is authenticated against the right account.
  2. Follow infra/README.md's one-time bootstrap: create the S3 state bucket + DynamoDB lock table, and the persistent musafir/db-master-password-persistent secret.
  3. Copy backend.hcl.example → backend.hcl and terraform.tfvars.example → terraform.tfvars; fill in real values, including github_oidc_sub (obtained via the debug workflow step documented in the README — don't guess it).
  4. Run terraform init -backend-config=backend.hcl from infra/environments/prod.
  5. Run terraform plan -var-file=terraform.tfvars and read through the plan.
  6. Run terraform apply -var-file=terraform.tfvars.
  7. curl -i https://<cloudfront-domain>/health.
  8. Check the ECS service reaches steadyState in the AWS Console or via aws ecs describe-services.
  9. From a machine outside the VPC, confirm you cannot reach the RDS endpoint on 5432 (connection should time out, not refuse) — proves the private-only security group is working.
  10. Run infra/scripts/backup.sh, then infra/scripts/destroy.sh, then infra/scripts/restore.sh to prove the full round-trip, following the two printed manual follow-ups at the end of the restore.

9. Known Issues and Limitations

  • No AWS CLI or Terraform were present in this environment at session start. Terraform 1.9.8 was downloaded as a portable binary (no admin rights available; chocolatey install failed on a permissions error) solely to run fmt/init/validate locally — it was never pointed at a real AWS account and created nothing in the cloud.
  • terraform validate caught a real bug: the GitHub Actions OIDC thumbprint_list values were first written from memory and were malformed (39 hex characters instead of the required 40, on two separate attempts) — and were for the wrong certificate authority entirely (an old DigiCert-era value; GitHub's token.actions.githubusercontent.com now serves a Let's Encrypt certificate). Fixed by computing the real SHA1 fingerprints directly from a live TLS handshake with openssl s_client, not from a remembered/published value. The module's comment documents the exact command to re-derive this if it ever needs to change.
  • github_oidc_sub, allowed_origins, and ai_api_key are required variables with no real values supplied — terraform apply will prompt for them (or fail non-interactively) until the user fills in terraform.tfvars.
  • No terraform plan/apply has been run against real AWS. Everything here is unverified against actual cloud behavior: IAM policy sufficiency (e.g. whether the deploy role's permissions are enough for the Phase 7 pipeline once it's written), RDS engine version availability in the chosen region, and CloudFront's interaction with the API in practice.
  • CI/CD workflows (Phase 7 — .github/workflows/deploy.yml that would actually push images and update the ECS service) are not part of this session's scope and don't exist yet, so the ECS service will have no image to run immediately after a first apply.
  • Old manual RDS snapshots from backup.sh are never pruned automatically — documented in the README as an accepted MVP gap, per backend-spec.md §9.
  • The CLAUDE.md instruction to open this report "in your Superset browser" couldn't be followed — no such tool/capability is available in this session (confirmed via a tool search). The file is saved locally; open it directly in any browser.
  • The CLAUDE.md instruction to prefer "Archify" for diagrams also couldn't be followed — no such tool is available in this session. The architecture diagram above is hand-authored inline SVG instead.
